# REQUIREMENTS.md — 3-Adventure（保守的アプローチ）

## 0. プロジェクト概要

3Dローポリキャラクターが登場する、ブラウザで遊べる bullet-heaven（Vampire Survivors型）サバイバーゲーム。
スマホ（タッチ操作、片手プレイ）での快適な操作を必須とし、PCでも遊べる。
キャラクター・武器は Meshy API 中心のパイプラインでほぼ自動生成し、開発者がキャラの追加/削除・武器の追加/削除を
JSON マニフェストの編集だけで行えることを目標とする。ゲーム実行時は外部APIを一切呼ばない（$0、静的ホスティング）。

このアプローチでは **実績のある技術・パターンの再利用、リスク最小化、保守性優先** を判断基準とする。
具体的には `robo-battle-v5-agent/tools/meshy-3d-studio`（Meshy クライアント・ジョブ管理・マニフェスト検証・
グレースフルデグレード）と `nova-clash-agent`（武器のボーンアタッチ・Blenderヘッドレス生成・プロシージャル
フォールバック）という、既に動作実績のある2つの社内リファレンス実装をほぼそのまま流用する。新規性より
「壊れない」ことを優先する。

## 1. ユーザーストーリー

### 1.1 プレイヤー（エンドユーザー）
- US-01: プレイヤーとして、スマホでバーチャルスティック1本を操作するだけで移動でき、攻撃は自動で行われてほしい（片手プレイ）。
- US-02: プレイヤーとして、時間経過とともに敵の物量が増していく緊張感を味わいたい。
- US-03: プレイヤーとして、レベルアップ時に3択から武器/スキルを選び、ビルドを組み立てたい。
- US-04: プレイヤーとして、ラン終了後も永続的に強くなる要素（メタ進行）があり、次のプレイに動機を感じたい。
- US-05: プレイヤーとして、PCではキーボード(WASD)+マウスで同等に遊べてほしい。
- US-06: プレイヤーとして、低スペックのスマホでもカクつかず遊べてほしい（描画品質が自動で落ちても構わない）。
- US-07: プレイヤーとして、ボスを撃破したときに明確な達成感（演出・報酬）がほしい。

### 1.2 開発者（アセットパイプライン運用者）
- US-08: 開発者として、ローカルスタジオ画面からMeshy APIでキャラクターを生成し、プレビューしてからゲームに登録したい。
- US-09: 開発者として、生成した3DモデルにMeshyの自動リグ（歩行/走行モーション付き）を適用し、Mixamoなど追加工程なしでゲームに使いたい。
- US-10: 開発者として、キャラクター・武器を JSON マニフェストの編集だけで追加・削除・無効化したい（コード変更不要）。
- US-11: 開発者として、不正なマニフェスト値（範囲外のステータス等）をゲーム起動前に検知したい（サーバー側・クライアント側の二重検証）。
- US-12: 開発者として、GLBファイルの読み込みに失敗しても、ゲーム全体がクラッシュせず代替表示で継続してほしい（グレースフルデグレード）。
- US-13: 開発者として、Meshyでの3D生成が失敗（リグ失敗・タイムアウト・APIエラー）しても、静的モデルや代替表現でゲームが成立してほしい。

## 3. 非機能要件（保守的判断）

- **性能**: 60fps を目標値とするが、ローエンドスマホでは自動的に描画品質・エフェクト密度・敵の同時描画数を落とし、
  30fps を実用下限として許容する（固定タイムステップのゲームループにより、フレームレートが変動してもロジックは破綻しない）。
- **互換性**: WebGL2 優先実装、WebGL1 検出時はシェーダー/ポストプロセスを簡略化したフォールバックパスに切替。
  iOS 18以降のSafari、最新Chrome/Edge/Firefoxを正式サポート対象とする。
- **保守性**: three.js の標準的な構成（シーングラフ、単純な `update(dt)` ゲームループ、オブジェクトプール）を採用し、
  独自フレームワークを作らない。ゲーム本体とスタジオツールはリポジトリ内で明確にディレクトリ分離する。
- **セキュリティ**: Meshy APIキー等の秘密情報はアプリ配下に置かず、`~/.config/ai-agents/` 側からパス参照する。
  スタジオツールはローカル開発専用（本番ゲームには同梱・公開しない）。
- **可用性/グレースフルデグレード**: Meshy生成・リグ・GLB読み込みのいずれかが失敗しても、プロシージャル代替表示で
  ゲームプレイ自体は継続可能であること（既存パターンの踏襲、後述 CRITICAL_PATH.md 参照）。
- **拡張性より安定性**: 武器シナジー等の高度な仕組みはMVP後の拡張とし、MVPでは「壊れない・面白さの核が成立する」
  最小構成に絞る。
- **コスト**: ゲーム実行時は外部API呼び出し $0（静的ホスティング）。開発時のMeshy生成コストのみ発生（別途 TECH_STACK.md で試算）。

## 4. MVP スコープ定義（保守的アプローチの核心）

**「1ステージ・キャラ3体・武器6種で、面白さのコアループが成立すること」を MVP 完成の基準とする。**

- ステージ: 1種類（見下ろし視点の閉じた/緩やかに区切られたフィールド）
- プレイアブルキャラクター: 3体（初期解放1体 + アンロック2体。差別化は移動速度・HP・専用アビリティ程度に留める）
- 武器: 6種（近接2・遠隔2・範囲2 を目安に、シナジーはMVPでは同時装備数上限のみの簡易実装）
- ボス: 1体
- 永続アップグレード: 3〜5項目（HP増加、移動速度増加、開始武器強化 等、シンプルなもの）
- 対応入力: バーチャルスティック（モバイル）+ WASD（PC）。ジャイロ操作は本ゲームでは必須要件に含めない
  （移動スティック1本で完結する設計のため。PROJECT_INFO.yaml の `mobile_features` は `touch_controls` /
  `virtual_joystick` であり `tilt_control` は含まれないことを確認済み）。

上記スコープを超える要素（武器シナジーの本格実装、複数ステージ、収集要素の拡充等）は MVP 後の拡張候補とし、
WBS.json 上は MVP クリティカルパスの外に置く。

## 5. 成功基準（テスト可能な形で定義）

- コアループ（移動→被弾/攻撃→レベルアップ選択→ウェーブ継続→ボス撃破）が最初から最後まで中断なくプレイできる。
- キャラクター/武器の追加を「マニフェストJSON編集 + GLB配置」のみで実施でき、ゲーム側コード変更が不要である
  （実装後、実際に1体追加してこれを検証する）。
- 意図的に壊れたGLBパス・不正な値を持つマニフェストエントリを与えても、ゲームがクラッシュせず代替表示で継続する。
- モバイル実機（iOS 18+ Safari を想定）とPCブラウザの両方で、縦横レスポンシブ・タップ操作が機能する。
- WebGL1のみの環境（エミュレーション含む）でフォールバックパスが動作しエラーが出ない。

## 6. リスクと対策（概要。詳細は CRITICAL_PATH.md）

- Meshyのリギング失敗・タイムアウト → 静的モデル+プロシージャル代替へのグレースフルデグレードを必須実装。
- モバイルWebGL性能不足 → オブジェクトプール必須化、WebGL1フォールバック、描画品質自動スケーリング。
- マニフェストの不正値によるランタイムエラー → サーバー/クライアント二重バリデーションを必須実装。
- スコープ肥大化 → MVP定義（3キャラ・6武器・1ステージ）をクリティカルパスの唯一のゴールとして厳守。
