## 3. ロジック/描画分離の設計原則

1. **依存の方向は一方向**: `render/` と `input/` は `logic/` と `cpu/` を参照してよいが、
   `logic/` と `cpu/` は `render/`・`input/`・DOM API・Canvas APIを一切import しない。
2. **状態の単一ソース**: ゲーム状態（`GameState`）は `state/game-state.ts` が保持し、
   `logic/` の関数群は基本的に「状態を受け取り、新しい状態（または副作用を伴う更新結果）を返す」形にする。
3. **副作用の局所化**: `chain-loop.ts` のようにループを伴う処理も、内部では純粋なステップ関数（`applyGravity`, `detectChains`, `resolveChainStep`）を組み合わせるだけにし、DOM操作や描画呼び出しを含めない。
4. **CPUもロジックの利用者**: `cpu/evaluator.ts` は `logic/` の関数（連結検出・重力シミュレーション）を呼び出して「もしこの手を打ったら」を仮想評価する。CPU層とロジック層の境界を明確にすることで、CPUの評価精度向上や難易度調整がロジックに影響を与えない。
5. **メインループの責務は「orchestration」のみ**: `game-loop.ts` は「入力を受け取る→ロジックを更新→CPUに手番を渡す→描画を呼ぶ→音声を鳴らす」という順序制御に徹し、個別のアルゴリズムを持たない。
6. **CPU思考の非ブロッキング化**: `cpu/scheduler.ts` が候補評価を複数フレームに分割して実行する（例: 1フレームあたり評価候補N件まで処理し、残りは次フレームに繰り越す）。これにより `game-loop.ts` の入力処理・描画は常に一定間隔で継続する。難易度が上がるほど評価候補数は増えるため、上級ほど数フレームに分散して思考する設計とする。

## 4. テスト容易性の確保

- `logic/` と `cpu/` の全モジュールは、DOM/Canvas/Web Audioに依存しないため、Vitestで直接インポートしてユニットテスト可能。
- 盤面状態は単純な2次元配列（またはフラット配列+幅高さ）で表現し、テストコードで盤面をリテラルとして直接記述できるようにする（可読性の高いテストケース作成のため）。
- `chain-loop.ts` の安全弁（最大反復回数）は定数化し、テストで「意図的に無限ループになりうる入力」を与えても有限回で終了することを検証する。
- `cpu/evaluator.ts` は入力（盤面・候補手）→出力（スコア数値）の純粋関数として設計し、期待値ベースのテーブルテストを可能にする。

## 5. パフォーマンス・レスポンシブ対応

- `render/canvas-scaler.ts` が `devicePixelRatio` とCSSサイズ（`clientWidth`/`clientHeight`）から論理解像度を計算し、`resize`イベントで再計算する。
- Canvas論理サイズは盤面の列数×セルサイズを基準にし、CSS側でmax-width/aspect-ratioを使って画面幅に追従させる。
- タッチ操作領域（`input/touch-input.ts`）はCSS上のヒットエリアを44px相当以上確保し、実際の判定はDOM要素のクリック/タッチイベントで行う（Canvas内の座標計算に依存しない設計とし、保守性を優先する）。

## 6. Phase 2 並列開発の差別化軸（検討過程・Phase 1時点の草案）

> **本節は技術選定（Phase 1）時点の検討過程の記録である。実装フェーズ（Phase 2）で実際に採用する確定版は8節「実装差別化戦略（Phase 2 並列開発・2案）」を正とする。** 本節と8節の内容に差異がある場合は8節を優先する（8節が本節を踏まえて確定させた最終決定であるため）。

静的なローカル完結ゲームであるため、サーバー構成の分岐（マイクロサービス/モノリシック/サーバーレス）は該当しない。
本プロジェクトで実際に意味のある違いを生む軸は「描画方式」「状態管理」「入力系」である。
保守的アプローチとしては、**過度な差別化はリスクを増やすため、2案を基本とし、必要なら3案目を軽量な出し方にする**。

### 案A: Canvas単一描画 + シンプルステートマシン（推奨・最保守的）
- **描画方式**: 盤面・ピース・エフェクトをすべて1枚のCanvasに集約し、`board-renderer`が毎フレーム全体を再描画するシンプルな方式。
- **状態管理**: `GameState`を素朴なオブジェクト＋switch文によるステートマシン（`'playing' | 'paused' | 'result'`）で管理。イベント駆動の複雑な仕組みを持たない。
- **入力系**: キーボードイベントリスナー＋タッチはボタン型UI（DOM要素のonclick）のみ。ジェスチャー認識は行わない。
- **差別化の狙い**: 実装量が最小で、バグの混入経路が少ない。学習コストが低く、後続の保守担当者が読みやすい。
- **現実性の根拠**: Canvas 2Dの単一再描画は小〜中規模の2Dゲームで実績が豊富であり、6×12マス程度の盤面描画負荷は現代ブラウザで余裕を持って60fpsを達成できる。

### 案B: レイヤー分割描画（背景/盤面/エフェクト） + Observerパターン状態管理
- **描画方式**: 背景・盤面・落下中ピース・エフェクト（消去演出等）を複数のCanvas（またはオフスクリーンCanvas）に分離し、変化の少ないレイヤーは再描画を間引く。
- **状態管理**: `GameState`の変更を購読者（描画・音声・UI）にイベントで通知するObserverパターン（軽量な自作Pub/Sub）を採用。
- **入力系**: キーボード＋タッチに加え、簡易スワイプジェスチャー（フリックで高速落下等）を追加。
- **差別化の狙い**: 描画パフォーマンスの最適化余地と、UIの疎結合化による拡張性を検証する。
- **現実性の根拠**: レイヤー分割・Pub/Subはいずれも枯れたパターンであり、ローカル完結の静的アプリでも実装リスクは低い。ただし案Aよりコード量・複雑度が増える。

### 案C（軽量な3案目・任意）: 状態管理をイミュータブル履歴方式にした案
- **描画方式**: 案Aと同じCanvas単一描画。
- **状態管理**: `GameState`を毎ステップ新しいオブジェクトとして生成し、直近数ステップの履歴を保持する（デバッグ・将来のリプレイ機能の布石）。
- **入力系**: 案Aと同じ。
- **差別化の狙い**: 「状態管理方式」のみを差別化軸にした最小差分の比較用。案A/Bほど工数をかけずに状態管理の違いによる保守性・テスト容易性の差を検証できる。
- **現実性の根拠**: 盤面データが小さい（6×12程度）ため、毎ステップの複製コストは無視できるレベルであり、パフォーマンスリスクなく試せる。

**推奨**: Phase 2では**案Aと案Bの2案**を並列開発することを推奨する（保守的アプローチとしては、無理に3案目を作らず、意味のある比較に絞る）。案Cは工数に余裕がある場合のみ追加候補とする。

### 8.1 なぜ2案なのか（3案目を採用しない理由）

本プロジェクトは静的ファイルのみで完結するブラウザ内ローカル完結ゲームであり、一般的なWebアプリで差別化軸になり得る「サーバー構成」（マイクロサービス/モノリシック/サーバーレスの比較、DB選定の比較、API設計の比較等）がそもそも存在しない。TECH_STACK.mdで確定した通り、実行時依存ゼロ・外部API不使用の構成であるため、サーバーレス vs マイクロサービスのような比較軸を用意しても本プロジェクトの実態に即さず、**3案目に意味のある差別化軸を見出せない**。

6節の検討過程では「状態管理をイミュータブル履歴方式にした案（案C）」を軽量な3案目の候補として記録したが、以下の理由から確定版では不採用とする。

- 案Cの差別化軸（履歴保持の有無）は案A・案Bいずれの描画アーキテクチャとも独立した小さな実装ディテールであり、UX評価（35%）に与える影響が乏しく、2案の比較に対して追加コスト（並列worktree・評価作業）に見合う情報が得られない。
- 本プロジェクトで実際にUX・保守性双方に大きな差を生むのは「描画アーキテクチャ（単一Canvas全再描画 vs レイヤードCanvas）」と「演出（ジュース感）の作り込み度合い」であり、この軸は案A・案Bの対比だけで十分にカバーされる。
- 保守的アプローチの基本方針（REQUIREMENTS.md、ARCHITECTURE.md冒頭）として「過度な差別化はリスクを増やす」ため、比較のための比較ではなく、意味のある2軸に絞る。

したがって、**Phase 2では案Aと案Bの2案のみを並列開発する**（案Cおよびそれ以外の分岐は行わない）。

### 8.2 両案に共通する前提

- **logic/・cpu/のコア実装は同一仕様**: `src/logic/`（board, piece, chain-detector, gravity, chain-loop, score, garbage, game-result）および `src/cpu/`（candidate-generator, evaluator, difficulty, scheduler）は、SPEC.md・data_models.md・API_DESIGN.mdに定義された仕様に完全準拠する形で、**案A・案Bの両worktreeで同一の入出力契約**を持つ。ゲームルール・CPU思考ロジック自体に案ごとの差異を設けない。
- **差別化軸は「描画アーキテクチャ」と「演出（UX）」のみ**: 両案の違いは `src/render/`（描画方式）・`src/state/`（状態通知方式）・演出の作り込み度合いに限定される。ARCHITECTURE.md 3節の依存原則（`logic/`・`cpu/`は`render/`・`input/`・`audio/`を一切importしない）は両案とも厳守する。
- **評価基準**: CLAUDE.mdに定義された評価基準（UX 35% / 機能完成度 20% / パフォーマンス 15% / テスト品質 15% / セキュリティ10% / 保守性5%）に従い、`autonomous_evaluator_ux.py` による自律評価でmainにマージする案を選定する。UXが最優先基準であるため、両案の設計思想もこれを踏まえたものとする。

### 8.3 案A「Canvas一体型・堅実設計」

- **worktree**: `phase2-impl-prototype-a`
- **描画方式**: 盤面・ピース・エフェクトをすべて1枚のCanvasに集約し、`board-renderer.ts` が毎フレーム全体を再描画する。オフスクリーンCanvasやレイヤー分離を行わない。
- **状態管理**: `GameState` を素朴なオブジェクト＋中央集権的なステートマシン（`game-loop.ts` がフェーズ（`'title' | 'difficultySelect' | 'playing' | 'paused' | 'result'`）に応じた分岐処理を直接持つ）で管理する。Observerパターンやイベントバスのような間接層を持たない。
- **演出**: 消去・カスケード・ブロッカー着弾等の演出は最小限（色の点滅、単純なフェード程度）に留め、実装の複雑度を抑える。
- **設計思想**: シンプルさ・確実な動作・保守性を最優先する。演出を絞ることで、バグの混入経路・状態不整合のリスクを最小化し、60fpsを確実に達成することを狙う。
- **狙うユーザー体験**: 「操作した通りに、遅延なく、崩れずに動く」という信頼感。派手さより堅牢さで評価を積み上げる。

### 8.4 案B「レイヤードCanvas・ゲームフィール重視」

- **worktree**: `phase2-impl-prototype-b`
- **描画方式**: 背景／盤面／ピース／エフェクトの4層相当にCanvas（またはオフスクリーンCanvas）を分離し、変化頻度の異なるレイヤーごとに再描画を最適化する。
- **状態管理**: `GameState` の変更を描画・音声・UI各購読者に通知する軽量なObserver（Pub/Sub）パターンを採用し、レイヤーごとに必要な更新のみを行う。
- **演出（ジュース感）**: パーティクル演出（消去時のセル飛散等）、画面シェイク（大連鎖・ブロッカー着弾時）、連鎖カットイン（「2 CASCADE!」等の演出テキスト表示）といった、手触り・爽快感を高める視覚効果を作り込む。
- **設計思想**: UX評価（35%、最優先基準）で明確に優位に立つことを狙った設計。描画の疎結合化により、演出の追加・調整がしやすいアーキテクチャとする。
- **狙うユーザー体験**: 「消した瞬間の気持ちよさ」「対戦の緊張感が画面から伝わること」。派手さと応答性の両立で評価を積み上げる。

## 1. なぜフレームワークを採用しないか（React不採用の根拠）

### 1.1 テンプレートの例外規定への該当

本ワークフローの標準方針では新規Webアプリに React 等のUIフレームワークを用いることが多いが、**「Canvas/WebGLベースのゲーム → vanilla + Canvas API」という明示された例外規定に該当する**ため、本プロジェクトでは React を採用しない。

理由:

1. **描画対象がDOMツリーではない**: Cascade Clash の主要な表示物（盤面・ピース・エフェクト・ネクスト表示）はすべて Canvas 2D 上に毎フレーム描画される。Reactの差分検出（Virtual DOM diffing）はDOM要素の更新最適化に強みがあるが、Canvas描画はReactの管理外で命令的に行う必要があり、Reactを挟んでも本質的な恩恵がない。
2. **状態更新の頻度と性質の不一致**: ゲームループは `requestAnimationFrame` で60fps駆動し、`GameState` は1フレームごとに新しいオブジェクトとして生成される（ARCHITECTURE.md 3節）。これをReactの `useState`/`useReducer` に載せると、不要な再レンダリング抑制のための `useMemo`/`useCallback`/`React.memo` のチューニングが常に必要になり、素朴なゲームループより複雑度が増す。
3. **保守性への逆効果**: N7（保守性、モジュール分割の徹底）はロジック層をフレームワーク非依存にすることで担保される。Reactを導入すると、ロジック層とUI層の境界にReactのライフサイクル（副作用・レンダリングタイミング）が入り込みやすく、「ロジック層はrender/input/audioを一切importしない」という一方向依存の原則（ARCHITECTURE.md 3節）を壊す誘因になる。
4. **バンドルサイズ・依存追加のリスク**: React本体・ReactDOMは実行時依存として `dependencies` に入り、N3（ビルド簡潔性）・「実行時依存ゼロ」方針と相容れない。

### 1.2 代替案比較表

| 案 | 概要 | 採用可否 | 理由 |
|---|---|---|---|
| **Vanilla TypeScript + Canvas 2D（採用）** | フレームワークなし、純粋関数中心のロジック層 + Canvas命令的描画 | ✅ 採用 | Canvas主体のゲームに最適。実行時依存ゼロ。テスト容易性が高い |
| React + Canvas ref | ReactコンポーネントからCanvas要素をrefで取得し内部で命令的描画 | ❌ 不採用 | Reactの恩恵（宣言的UI）がCanvas内部描画には及ばず、DOM側UI（メニュー等）のためだけに大きな依存を追加することになり費用対効果が低い |
| React + SVG/DOM描画 | 盤面もDOM要素として描画 | ❌ 不採用 | 6×12マス×2盤面の頻繁な再描画をDOM要素で行うとレイアウト再計算コストが増え、60fps目標（N4）に対してCanvasより不利。過去の実績（保守的アプローチ）でもCanvasが定石 |
| Vue / Svelte 等の軽量フレームワーク | Reactより軽量な代替 | ❌ 不採用 | 軽量でも「Canvas主体でDOM操作が薄い」という本プロジェクトの性質上、恩恵よりフレームワーク学習・保守コストが上回る |
| WebGL（Three.js/PixiJS等） | GPU描画による高性能化 | ❌ 不採用 | 6×12マス程度の2D盤面描画にWebGLはオーバースペック（ARCHITECTURE.md 1節に既記載）。ライブラリ依存も増え、保守的アプローチのリスク最小化方針に反する |

## 2. 各技術要素の選定理由

### 2.1 言語: TypeScript（strict mode）

- **理由**: 型安全性により `GameState`/`Board`/`Piece` 等の複雑な状態遷移のバグを実装時・コンパイル時に検出できる。data_models.md の型定義がロジック層・CPU層・描画層共通の「単一ソース」として機能し、レイヤー間の型不整合をコンパイラが検出する。
- **strict mode を有効化する理由**: `null`/`undefined` の扱い（例: `PlayerFieldState.activePiece: Piece | null`）を厳格にチェックすることで、N9（エラー耐性）に資する。
- **代替案**: JavaScript（型検査なし）→ 不採用。中規模のステートマシン・連鎖ロジックを持つ本プロジェクトでは型検査による早期バグ検出の価値がコストを上回る。

### 2.2 ビルドツール: Vite

- **理由**: 設定ファイルが最小限（`vite.config.ts` 1ファイル）で `npm install` → `npm run build` の2手順を満たせる。開発時は `npx vite dev` でHMR付きローカル実行が即座に可能。Vitest・Playwrightとの親和性が高く、追加の統合設定が不要。
- **`base: './'` の設定**: 将来のGitHub Pages公開（プロジェクトページ、例: `https://<user>.github.io/cascade-clash/`）を想定し、ビルド成果物の参照パスをすべて相対パスにする。これにより、ローカル実行（`launch_app.command` からのファイル配信/簡易サーバー）とGitHub Pages公開のどちらでもパス崩れが起きない。
- **代替案比較**:
  | 案 | 不採用理由 |
  |---|---|
  | webpack | 設定量が多く、保守的アプローチの「ビルド構成の複雑化を避ける」方針（REQUIREMENTS.md R7）に反する |
  | esbuild単体 | Vitest/Playwrightとの統合や開発サーバー機能を自前で組む必要があり、Viteより工数が増える |
  | バンドラなし（素のTS→JSトランスパイルのみ） | 開発体験（HMR、依存解決）が大きく劣り、モジュール分割（ARCHITECTURE.md 2節の多数ファイル構成）の管理が煩雑になる |

### 2.3 描画: Canvas 2D API

- **理由**: 盤面・ピース・エフェクトの矩形/円形描画中心のパズルゲームに実績豊富なAPI。`devicePixelRatio` 対応の解像度計算（ARCHITECTURE.md 5節）も標準APIの範囲で完結する。
- **画像ファイルを一切使わない方針**: すべてのビジュアル（ピース、シンボル、背景、エフェクト）を `CanvasRenderingContext2D` の図形描画命令（`fillRect`/`arc`/`fillText`等）で生成する。これにより (1) 画像アセットの権利チェックが不要になる、(2) ビルド成果物のファイル数・サイズが最小化される、(3) IMAGE_PROMPTS.json のような画像生成プロンプト定義自体が不要になる（5節で詳述）。
- **代替案**: WebGL → 2.1節で不採用理由を既述（オーバースペック）。DOM/CSSのみでの盤面描画 → 頻繁な再描画・アニメーションでレイアウトスラッシングのリスクがありCanvasに劣る。

### 2.4 テスト: Vitest + Playwright

- **Vitest（ユニットテスト）**
  - 理由: Viteと設定を共有でき、TypeScriptを追加のトランスパイル設定なしで直接実行可能。`logic/`・`cpu/` はDOM/Canvas非依存の純粋関数中心（ARCHITECTURE.md 4節）であるため、Vitestで高速に大量のテーブルテストを実行できる。
  - 代替案: Jest → Viteプロジェクトでは追加のトランスフォーム設定（ts-jest等）が必要になり、Vitestより統合コストが高いため不採用。
- **Playwright（E2Eテスト）**
  - 理由: 実ブラウザ（Chromium/WebKit/Firefox）でのE2E実行が可能。モバイルデバイスエミュレーション（タッチ操作の検証、N5・R4対応）が標準機能として組み込まれている。
  - 代替案: Cypress → モバイルタッチエミュレーションやマルチブラウザ対応の面でPlaywrightに劣り、不採用。

### 2.5 Lint・型検査: ESLint + `tsc --noEmit`

- 理由: 標準的な構成であり追加ツール（Biome等の新興ツール）を持ち込まずシンプルに保つ（保守的アプローチの基本方針）。`tsc --noEmit` はビルドとは独立に型検査のみを実行し、CIやローカルの `npm run typecheck` 相当のコマンドで高速に検証できる。

### 2.6 永続化: `localStorage`

- 理由: 効果音ON/OFF設定（F-31）のみを永続化する軽量用途であり、サーバー不要要件（N3, N5）を満たす最小の手段。N10（セキュリティ）に従い、読み書きは必ず例外処理でラップする。

## 3. 実行時依存ゼロ方針

`package.json` の `dependencies` は空（`{}`）とし、Vite・TypeScript・Vitest・Playwright・ESLint関連はすべて `devDependencies` に置く。

**理由**:
- ビルド後の成果物（`dist/` 相当）はプレーンなHTML/CSS/JS（Canvas描画・Web Audio API呼び出しのみ）であり、実行時に外部ランタイムライブラリを読み込む必要がない。
- 依存パッケージ数を最小化することで、サプライチェーンリスク（悪意あるパッケージ更新等）を構造的に低減する。
- ローカル実行・将来のGitHub Pages公開のいずれも「静的ファイルの配信」のみで完結し、Node.jsサーバーやランタイム依存を持たない。

**ビルド手順（確定）**:
```bash
npm install       # devDependenciesのみインストール
npm run build     # Viteによる本番ビルド（dist/にHTML/CSS/JS出力）
```

**ローカル開発実行**:
```bash
npx vite dev      # HMR付き開発サーバー（ローカルのみ、外部通信なし）
```

## 5. 外部API — 正式決定: 一切使用しない

### 5.1 決定内容

以下の外部API・課金APIは **本プロジェクトでは一切使用しない**。これは開発方針の検討漏れではなく、正式な決定事項である。

| API | 用途（もし使うなら） | 決定 |
|---|---|---|
| Vertex AI Imagen | ゲーム内画像・アイコン等の生成 | **不使用** |
| Lyria（音楽生成API） | BGM・効果音の生成 | **不使用** |
| Text-to-Speech（TTS） | 音声ガイダンス・ナレーション等 | **不使用** |
| その他の外部課金API全般 | — | **不使用** |

### 5.2 理由

1. **ユーザーからの明示指示**: 「課金APIを無断で使用せず、CSS/Canvas/Web Audio等ローカル技術を優先する」という明確な指示があり、これを本プロジェクトの技術選定における最上位制約として扱う。
2. **要件との整合性**: REQUIREMENTS.md N5（外部CDN・外部フォント等の実行時ネットワーク依存を持たない）、N10（外部API不使用による攻撃面の限定）、SPEC.md 7.3節（外部通信を一切行わない）と完全に整合する。むしろ画像・音楽・音声の生成に外部APIを使うと、これらの既存要件と矛盾することになる。
3. **ゲームの性質との適合**: Cascade Clash は図形・色・波形合成で表現が完結するジャンル（パズルゲーム）であり、写実的な画像やナレーション音声を必要としない。Canvas描画・Web Audio APIのみで要件（US-12〜US-15, F-30〜F-34等）を十分に満たせる。
4. **コスト・運用リスクの排除**: 課金APIを使わないことで、4節のコスト試算が恒久的に $0 になり、APIキー漏洩・レート制限・サービス停止等の外部依存リスクも排除される。

### 5.3 画像生成・音楽生成プロンプト定義ファイルについて

通常のワークフローでは画像生成用に `IMAGE_PROMPTS.json`、音楽/音声生成用に `AUDIO_PROMPTS.json` を作成する場合があるが、**本プロジェクトではこれらのファイルを生成しないという判断を明示的に記録する**。

- **`IMAGE_PROMPTS.json`**: 生成不要。理由: 画像ファイル自体を使用しない（2.3節）。ピース・背景・UI・エフェクトはすべて `render/` 配下のCanvas描画関数がその場で図形として描く。
- **`AUDIO_PROMPTS.json`**: 生成不要。理由: 音源ファイルを使用しない。効果音は `audio/sound-engine.ts` が `OscillatorNode`/`GainNode` 等でパラメータ（周波数・エンベロープ）から都度波形合成する（ARCHITECTURE.md 7節にも同様の記載あり）。

この判断はPhase 1（技術選定）の時点で確定し、以降のPhase（実装・品質改善・公開）でも覆さない。もし将来的に外部API利用が必要と判断される場面があっても、事前にユーザーへ確認し明示的な承認を得るまでは着手しない。

## 6. 音・画像の技術詳細（参考: ARCHITECTURE.md 7節と対応）

### 6.1 音: Web Audio API 波形合成

- `AudioContext` を生成し、`OscillatorNode`（波形: sine/square/triangle等）+ `GainNode`（音量エンベロープ: attack/decay）の組み合わせで効果音を都度合成する。
- 対象効果音: 設置音・消去音・カスケード音・警告音・勝敗音（SPEC.md F-30）。
- 自動再生ポリシー対応: `AudioContext` の生成・`resume()` は必ずユーザーの初回操作（クリック/タップ）イベント内で行う（REQUIREMENTS.md R8 / CRITICAL_PATH.md T040注記）。
- 録音サンプル・外部音源ファイルの読み込み機構自体を実装しない（アーキテクチャ上、audioファイルローダーを持たせないことで構造的に担保する）。

### 6.2 画像: Canvas描画のみ

- ピースの配色・形状・シンボル（色覚多様性配慮のシンボル、SPEC.md 7.2節）はすべて `render/piece-renderer.ts` 内の図形描画関数として実装する。
- 背景・エフェクト（消去演出、警告表示等）も同様にCanvas上の図形・グラデーション・パーティクル的な矩形/円描画で表現する。
- 画像ファイル（PNG/JPG/SVG等）は一切バンドルに含めない。

## 7. 可搬性・ブラウザ対応

- 対象: モダンブラウザ（Chrome/Edge/Safari/Firefoxの直近2メジャーバージョン、REQUIREMENTS.md N5）。
- 使用するWeb標準API（Canvas 2D、Web Audio API、`requestAnimationFrame`、`localStorage`）はいずれも対象ブラウザで安定してサポートされており、ポリフィルや追加ライブラリを必要としない。
- 外部CDN・外部フォントへの実行時参照を持たない（フォントはブラウザ標準のシステムフォント/`sans-serif`指定等に限定する）。

## 8. まとめ

本プロジェクトの技術スタックは、「ロジックと描画の分離」「実行時依存ゼロ」「外部API不使用（$0運用）」の3点を軸に、実績のある枯れた技術（Vanilla TypeScript, Vite, Canvas 2D, Vitest, Playwright）のみで構成する。この構成により、REQUIREMENTS.mdの非機能要件（N2, N3, N5, N10）およびユーザーの明示指示（課金API不使用）の双方を矛盾なく満たす。
